# Харнесс кодового агента на базе openJiuwen (openJiuwen Challenge 2026)

Харнесс получает каталог с задачами, сам решает, какие из них брать, и для каждой решённой задачи
создаёт `answer.txt`. Главная идея: **токены тратятся только там, где без модели нельзя**.

| Уровень | Что делает | Цена |
|---|---|---|
| 0. Детерминированные решатели | math, data_analysis, search решаются обычным кодом на стандартной библиотеке | 0 токенов |
| 0. Проверки невыполнимости | нет сущности/файла/колонки, деление на ноль, противоречивые тесты и т. п. → задача пропускается | 0 токенов |
| 1. Ремонт кода мутациями | coding: классический generate-and-validate — одиночные правки AST, принимаются только если проходят тесты задачи | 0 токенов |
| 2. LLM через openJiuwen | всё, что не удалось понять или починить бесплатно: компактный запрос к модели без рассуждений (`qwen3.8-27b-noreason`), ответ проверяется тестами или исполнением кода | измеряется по `usage`; на реальных моделях не измерено |

На 8 опубликованных примерах харнесс набирает 20/20 баллов и тратит 0 токенов (см. «Проверка»).

## Сборка и запуск

```bash
docker build -t hack:latest .

# запуск командой из регламента; общий бюджет передаётся переменной BUDGET
docker run --rm --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

Локально без Docker (Python 3.11):

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt -c constraints.txt
LLM_BASE_URL=... LLM_API_KEY=... .venv/bin/python run_agent.py --tasks-dir /path/to/copy/of/tasks
```

Для уровней 0 и 1 не нужны ни openJiuwen, ни прокси: `python run_agent.py --tasks-dir <каталог>` работает
на чистом Python 3.11.

- Базовый образ `python:3.11.9-slim-bookworm`; единственная зависимость — `openjiuwen==0.1.19`
  (`requirements.txt`), все транзитивные зависимости зафиксированы в `constraints.txt`. Сборка строгая:
  если хоть одна зафиксированная версия не ставится или openJiuwen не импортируется, `docker build`
  завершается ошибкой (запасной установки без `constraints.txt` нет). Системные пакеты не ставятся.
- Собственные решатели написаны на стандартной библиотеке. При этом сам openJiuwen тянет за собой
  крупные пакеты (в образе есть, например, pandas, numpy, transformers) — харнесс их не использует, но
  они входят в размер образа (1,4 ГБ при лимите 4 ГБ). Локальные нейросети не запускаются.
- При запуске ничего не скачивается. Единственный сетевой адрес, к которому обращается харнесс, —
  `LLM_BASE_URL`.
- Ключ берётся только из переменной окружения `LLM_API_KEY`; в репозитории и в образе ключей нет.

## Как устроен прогон

```
run_agent.py
 └─ pipeline.run
     ├─ tasks.discover_tasks        task.json → task_id, task_type, instruction, reward (и только они)
     ├─ фаза 1 (0 токенов)          все задачи; ответ пишется сразу, как только он известен
     │    ├─ math_solver            цепочка шагов над числом коробок
     │    ├─ data_solver            вопрос → фильтры + метрика → расчёт по CSV
     │    ├─ search_solver          kb → карточки; сущность + цепочка связей
     │    └─ coding_solver          прогон тестов → проверки невыполнимости → ремонт мутациями
     └─ фаза 2 (LLM)                только задачи, оставшиеся «непонятыми»
          ├─ оценка стоимости, порядок по reward / оценка
          ├─ coding_solver.solve_llm   модель возвращает исправленные функции, тесты проверяют
          └─ llm_fallback.solve        модель пишет короткий Python, харнесс его исполняет
```

Каждый бесплатный решатель возвращает один из трёх вердиктов:

- `solved` — ответ известен, записывается немедленно;
- `infeasible` — невыполнимость **доказана** данными задачи, LLM не вызывается, `answer.txt` не создаётся;
- `unknown` — решатель не уверен. Задача уходит в очередь LLM. Угадывание запрещено: парсер обязан
  объяснить каждое слово вопроса, иначе он отказывается от ответа.

### math

Условие режется на предложения; служебные («Compute it with the bash tool…», «Work only inside…») отбрасываются.
Первое предложение должно задавать начальное число коробок, последнее — быть вопросом о конечном числе,
каждое промежуточное — целиком совпасть с одним из шаблонов шага: разделить поровну на N и оставить одну
долю (округление вниз/вверх), удвоить/утроить, отгружать X в день D дней, получить N поставок по M,
просто ±X. Поддерживаются синонимы (`ships / sends out / sells`, `deliveries / shipments / batches`,
`Then / Next / After that`). Любое нераспознанное предложение → `unknown`.

### data_analysis

Вопрос раскладывается на фильтры и метрику. Фильтры: `product 'widget'`, `region 'west'`, значения без
кавычек, `months 5 through 6 inclusive`, `between months 5 and 6`, `month 7`, списки `months 3 and 7`,
сравнения (`price above 50`). Метрики: сумма колонки (`how many units … were sold`), число строк,
выручка `units * price`, среднее / минимум / максимум / медиана, arg-max по группе
(`which region sold the most units`), число уникальных значений. Расчёт ведётся в рациональных числах,
без плавающей точки. Если после вычёркивания фильтров остаток вопроса не совпал целиком с шаблоном
метрики — `unknown`.

### search

Каталог `kb/` читается в карточки «имя → {ключ: значение}» (заголовок `# Имя`, строки `Ключ: значение`).
В вопросе ищется ровно одна сущность из kb и слова-связи: `born`, `employer / works for`, `mentor`,
`headquarters / headquartered / based`, `founded / established`, а также любые ключи, встречающиеся в
самой kb. Порядок цепочки (`X → employer → headquarters`) определяется грамматикой вопроса и
проверяется по данным: проходит только типово-корректная цепочка (у человека нет `Headquarters`).
Тип ожидаемого ответа («In which year…», «In which city…») сверяется с найденным значением.

### coding

1. Имена файла тестов и библиотеки берутся из инструкции. Если файл тестов в инструкции не назван, а в
   workspace их несколько, обязательными считаются все (один из нескольких молча не выбирается).
   Тесты запускаются на копии workspace в `/tmp` через `python -m unittest -v <модуль>` — это не зависит
   от наличия `unittest.main()` в файле; файлы с функциями `test_*` без классов исполняются встроенным
   раннером на `unittest.FunctionTestCase`. Прогон считается зелёным, только если: раннер сообщил `OK`,
   выполнено не меньше тестов, чем видно в файле статически, хотя бы один тест не пропущен, упавших нет.
   Код возврата 0 сам по себе успехом не считается. Если в файле нет исполнимых тестов, все тесты
   пропущены или тест-функции требуют фикстур pytest — задача не объявляется решённой и в LLM не
   отправляется (подтвердить успех было бы нечем). `async def`-тесты на уровне модуля действительно
   исполняются (`asyncio.run`), методы `IsolatedAsyncioTestCase` — штатно; `async def`-метод в обычном
   `TestCase` unittest не дожидается, поэтому такой файл считается неподдерживаемым, а не пройденным.
   Тесты уже проходят → `DONE`.
2. Ремонт мутациями (`solvers/mutations.py`): для функций, на которые ссылаются упавшие тесты, строятся
   одиночные правки AST — обращение операторов (`+`↔`-`, `<`↔`>`, `==`↔`!=`), замены парных функций
   (`sorted`↔`reversed`, `min`↔`max`), константы ±1, срезы, границы `range`, `return` внутри цикла и т. д.
   Варианты упорядочены по рангу «типичности» бага. Вариант принимается, только если множество упавших
   тестов строго уменьшилось и ни один прежде зелёный тест не упал; несколько багов чинятся за несколько
   раундов. Это обычный алгоритм автоматического исправления программ, без нейросетей.
3. Если мутации не помогли — LLM (см. ниже).
4. `mylib.py` в workspace заменяется (атомарно) только версией, прошедшей тесты на копии. После установки
   делается свежая копия workspace, проверяется, что файлы тестов побайтно совпадают с исходными, и тесты
   запускаются ещё раз на установленной версии. Если эта проверка не зелёная — исходная библиотека
   возвращается на место. `DONE` пишется только после неё. Файлы тестов не изменяются никогда.

Ремонт мутациями можно отключить переменной `HARNESS_MUTATION_REPAIR=0` — тогда coding идёт сразу в LLM.

### LLM-уровень (openJiuwen)

Вызовы идут через модельный слой openJiuwen:

```python
from openjiuwen.core.foundation.llm import init_model
model = init_model("OpenAI", model_name, api_key, api_base, temperature=0.0, timeout=..., verify_ssl=True)
msg = await model.invoke(messages, model=..., max_tokens=..., temperature=0.0)
msg.content; msg.usage_metadata.input_tokens / .output_tokens / .reasoning_tokens
```

- **coding**: один запрос — библиотека, исходники упавших тестов, сообщения об ошибках. Модель возвращает
  только исправленные функции; харнесс вклеивает их по именам и проверяет тестами. До трёх попыток,
  все по умолчанию на модели без рассуждений; каждая следующая попытка делается, только если она
  помещается в остаток потолка задачи (после двух дорогих попыток третьей не будет). Патч, который
  трогает тестовый раннер (`unittest`, `sys.exit` и т. п.), отклоняется без запуска. Модель может
  ответить `INFEASIBLE`.
- **остальные типы** (нераспознанные формулировки): модель получает условие без служебных фраз и
  краткое описание файлов (список, первые строки) и пишет короткую программу на Python. Харнесс исполняет
  её на копии workspace; одна строка вывода принимается как ответ, иначе вывод возвращается модели
  (до трёх шагов). Арифметику и чтение данных делает Python, а не модель — поэтому хватает модели без
  рассуждений. Модель может ответить `INFEASIBLE`.
- Температура 0, жёсткий `max_tokens` на каждый вызов.
- В запрос попадают только четыре документированных поля задачи и файлы данных из workspace. Служебный
  `task.json`, прежние `answer.txt` и всё, что лежит вне workspace (включая цели символических ссылок),
  в список файлов, превью и копию не попадают — за это отвечает один модуль `wsfiles.py`. Служебный файл
  скрыт и под другим именем: символическая или жёсткая ссылка на него (в том числе вложенная и цепочка
  ссылок) отбрасывается, ссылки на обычные данные внутри workspace работают.

Обработка ошибок прокси (`llm.py`):

| Ситуация | Поведение |
|---|---|
| 401 / 403 | ключ отклонён: LLM-уровень останавливается сразу, без повторов (попытки авторизации ограничены) |
| 400 / 404 / 422 | ошибочный запрос: не повторяется, остальные запросы продолжаются |
| 429, 5xx, сетевые ошибки | до 4 попыток с экспоненциальной задержкой и jitter, учитывается `Retry-After`; задержка общая для всех параллельных сессий и не выходит за дедлайн прогона. После полностью неудачного вызова клиент «остывает» и затем восстанавливается, а не выключается до конца прогона |
| 429 / 403 с однозначным сообщением об исчерпании общего бюджета (без `Retry-After` и без признаков временного лимита), либо 402 | останавливает LLM-уровень только после второго такого ответа подряд. Rate limit, «limit exceeded», квота токенов в минуту (TPM) и любой ответ с `Retry-After` — временные: повторы и восстановление |
| тайм-аут или потеря ответа после отправки | запрос мог быть выполнен и оплачен: зарезервированная оценка списывается как «неопределённый расход», повтор не больше одного раза |

Ошибка HTTP, пришедшая через openJiuwen, — это ответ прокси, а не поломка транспорта: запрос повторяется
тем же транспортом и не дублируется через запасной HTTP-клиент. Запасной клиент (стандартная библиотека)
используется, только когда сломана клиентская сторона openJiuwen или он не может установить соединение.
Сертификаты TLS всегда проверяются (системные CA и certifi); перехода на непроверяемое соединение нет.
- Запасной транспорт: если вызов через openJiuwen завершился ошибкой, тот же запрос повторяется обычным
  HTTP-клиентом стандартной библиотеки к тому же `LLM_BASE_URL`. Так поломка зависимости не обнуляет прогон.

## Оценка расхода токенов

Учёт по правилам соревнования: `стоимость = выходные + входные / 10`; токены рассуждений считаются
выходными. Числа берутся из `usage` каждого ответа прокси (`budget.py`). Входят ли токены рассуждений в
`completion_tokens`, определяется по структуре `usage`, а не сравнением величин: вложенное
`completion_tokens_details.reasoning_tokens` — это расшифровка `completion_tokens` (не прибавляется);
отдельное поле при `total = prompt + completion + reasoning` прибавляется; если понять нельзя —
прибавляется с пометкой о неопределённости в траектории. Ответ без `usage` не считается бесплатным:
стоимость оценивается по длине запроса и ответа, запись помечается как оценка.

Учёт харнесса — это его собственная бухгалтерия. Настоящий лимит применяет прокси, и сверить с ним
расход харнесс не может; при тайм-аутах расход оценивается с запасом (см. таблицу ошибок выше).

Прогноз до вызова:

1. Задачи, решаемые уровнями 0 и 1, стоят 0 — это не оценка, а факт: бесплатный решатель просто
   выполняется, и по его вердикту задача либо закрыта, либо попадает в очередь LLM.
2. Для задач очереди оценка строится по реальному тексту запроса, который будет отправлен:
   `(длина запроса в символах / 3,2) / 10 + ожидаемый вывод`, с запасом на повторную попытку.
   Для coding ожидаемый вывод — размер функций, на которые ссылаются упавшие тесты (× 1,6 + 80, в пределах
   160–1200); для остальных типов — 160 токенов на шаг, коэффициент 1,5.
3. Очередь сортируется по убыванию `reward / оценка`: при нехватке бюджета первыми идут самые выгодные
   задачи. Это жадная эвристика, а не оптимальное решение задачи о рюкзаке: она не учитывает вероятность
   успеха, оставшееся время и рост стоимости после неудачной попытки.

Контроль бюджета:

- общий бюджет берётся из переменной окружения **`BUDGET`** (взвешенные токены: выходные + входные / 10);
  его величина заранее не предполагается. `BUDGET` важнее старой `TOKEN_BUDGET`. `BUDGET=0` — платных
  вызовов нет, бесплатные решатели работают. Пустое, отрицательное, нечисловое или бесконечное значение
  не превращается в разрешение тратить: платные вызовы отключаются с сообщением в логе, бесплатный этап
  выполняется. Только если нет ни `BUDGET`, ни `TOKEN_BUDGET`, харнесс ограничивает себя величиной
  1000 × число задач — это локальное допущение, оно так и названо в логе и траектории (`budget_source`);
- мягкий лимит 85 % бюджета: перед каждым вызовом резервируется `входные/10 + max_tokens`; вызов, не
  помещающийся в лимит, не делается;
- каждая попытка, включая повтор после тайм-аута или ошибки, допускается отдельно: проверка лимита
  задачи и атомарный резерв → отправка → закрытие резерва и ровно одно списание (фактический `usage`
  либо зарезервированная оценка, если ответ потерян после отправки). Повтор, который уже не помещается в
  бюджет, не отправляется. Фактический расход выше оценки записывается как есть;
- лимит на одну задачу (все её попытки). Заданный владельцем `HARNESS_TASK_CAP` — жёсткий потолок. Без
  переменной 1800 — гарантированный минимум: задача может продолжить сверх него, пока укладывается в свою
  равную долю свободного сейчас бюджета (остальные доли — за задачами очереди, ещё не получившими первую
  попытку). Максимум трёх логических попыток на задачу сохраняется. Причина отказа в очередной попытке
  пишется точно (лимит задачи или общий бюджет, расход, остаток, оценка входа) в лог и в событие
  `attempt_denied`; отложенная из-за бюджета задача невыполнимой не считается;
- до 4 параллельных LLM-сессий (правила разрешают 5);
- временные ошибки прокси не выключают LLM-уровень (см. таблицу выше); уже записанные ответы остаются
  при любом исходе;
- общий таймер 50 минут. Бесплатный поиск мутаций ограничен 90 с на задачу и в сумме половиной времени
  прогона, когда LLM настроен, — чтобы не вытеснять платную работу. Кандидаты отправляются на проверку
  небольшими порциями, после дедлайна новые не отправляются, идущие запуски обрываются по дедлайну.

Прогноз и фактический расход каждого вызова пишутся в траекторию (`estimated_cost` и `cost`).

## Поиск невыполнимых задач

Невыполнимость распознаётся до обращения к модели. Задача отклоняется бесплатно только при доказательстве
из данных; в сомнительных случаях решает LLM, которой разрешён ответ `INFEASIBLE`.

| Тип | Что считается доказательством |
|---|---|
| math | деление на ноль («split equally into 0 warehouses»); количество не задано («ships some boxes per day», «starts with an unknown number of boxes») |
| data_analysis | нет файла, названного в условии; файл пуст; колонка, обещанная в условии и нужная для ответа, отсутствует в файле; в нужной числовой колонке стоят `n/a` и подобное; среднее/минимум/максимум по пустой выборке |
| search | нет каталога kb; сущность из вопроса нигде в kb не упоминается; нет карточки или факта, нужного в цепочке; две карточки одной сущности противоречат друг другу |
| coding | нет файла тестов или библиотеки; синтаксическая ошибка в файле тестов (его нельзя править); тесты импортируют несуществующий модуль; два утверждения требуют разных результатов одного и того же вызова; упавший тест не обращается к библиотеке |

Два правила, снижающие риск ошибки:

- Вердикты «нет в kb» выносятся, только если разобраны все файлы kb (иначе — `unknown` и LLM).
- Если ответ формально вычислим, он записывается, даже когда задача похожа на невыполнимую (например,
  товара нет в таблице → сумма `0`). За невыполнимые задачи баллы не начисляются при любом исходе, запись
  бесплатна, а ложный отказ от выполнимой задачи стоил бы баллов.

## Выбор модели

| Вызов | Модель | Почему |
|---|---|---|
| все попытки по умолчанию (coding и запасной агент) | `qwen3.8-27b-noreason` | нет токенов рассуждений (они оплачиваются 1:1); результат всё равно проверяется тестами или вычисляется Python |
| последняя попытка, только если задано явно | `HARNESS_MODEL_STRONG=qwen3.8-27b` | модель с рассуждениями — осознанное включение: её расход на этих промптах нами не измерен |

Модели переопределяются переменными `HARNESS_MODEL_FAST` и `HARNESS_MODEL_STRONG` (допустимы только
четыре модели соревнования). Расход на задачу зависит от задачи и не обещается заранее: он измеряется
по `usage` и виден в траектории.

## Траектории

Харнесс пишет траекторию в JSONL: по строке на событие (`run_start`, `outcome`, `planned`, `llm_call`,
`coding_attempt_failed`, `fallback_step`, `run_end`). В `llm_call` сохраняются сообщения запроса, ответ
модели, число токенов, прогноз и фактическая стоимость. По умолчанию файл создаётся в `/tmp`
(файловая система образа только для чтения); путь задаётся параметром `--trace`.

| `examples_llm_tier_MOCK.jsonl` | те же примеры с `HARNESS_MUTATION_REPAIR=0` плюс две короткие задачи для запасного агента (одна без `workspace/`): всё идёт через LLM-уровень и транспорт openJiuwen, прогон в Docker-образе. **Ответы давал локальный mock-прокси (`tests/mock_llm_server.py`) с заготовленными репликами, а не модели организаторов** — файл показывает формат запросов, учёт токенов и ход работы, но не качество моделей |

Всё перечисленное лежит в `tests/` и в образ не попадает (`.dockerignore` — белый список).

## Неочевидные детали

- **Поля `expected` и `check` харнесс не использует.** `tasks.py` оставляет из `task.json` только
  `task_id`, `task_type`, `instruction`, `reward`; остальное отбрасывается сразу после разбора JSON.
- **Файловая система только для чтения.** openJiuwen при импорте создаёт `./logs/` в текущем каталоге,
  поэтому `run_agent.py` первым делом переходит в `/tmp/harness_*`. Байт-код не пишется
  (`PYTHONDONTWRITEBYTECODE=1`), в workspace задач не появляется `__pycache__`.
- **Где лежит `answer.txt`.** Обязательный результат — `<задача>/answer.txt` (регламент: «в каталоге
  каждой задачи»). Задача считается отвеченной, только если именно этот файл записан и при обратном
  чтении побайтно совпал с вычисленным ответом; старый файл успехом не считается. Вторая копия кладётся в
  `<задача>/workspace/answer.txt` («текущий каталог» из инструкции), но обязательную запись не заменяет.
  Ответ заканчивается переводом строки (как `echo 42 > answer.txt`).
- **Запись атомарна.** Временный файл в том же каталоге → `flush` + `fsync` → `os.replace` → `fsync`
  каталога. До `replace` прежний файл остаётся целым, временный файл при ошибке удаляется. Так же
  устанавливается исправленный модуль в coding-задачах.
- **Права на запись — требование к запуску, а не к харнессу.** Контейнер работает как uid 0, но с
  `--cap-drop ALL`, то есть без `CAP_DAC_OVERRIDE` и `CAP_FOWNER`: на него действуют обычные права Unix.
  Чтобы ответы можно было создать, каталоги задач в `$TASKS` должны быть доступны на запись для uid 0
  по обычным битам: владелец root, либо `chmod -R a+rwX "$TASKS"`, либо подходящие группа/ACL. Если
  каталог принадлежит другому пользователю и имеет режим `755`/`775`, записать ответ изнутри невозможно
  ни повторными попытками, ни `chmod` — харнесс этого и не изображает: в начале прогона он один раз
  пишет в лог, сколько каталогов недоступно (владелец, режим, uid процесса), такие задачи остаются
  `unsolved` с причиной, остальные результаты не затрагиваются, код возврата 0. Проверено на сервере:
  копия с владельцем `1000:1000` и режимом `775` → 0 ответов и явная диагностика; та же копия после
  `chmod -R a+rwX` → все ответы на месте. Какие права будут у `$TASKS` в финальном запуске, регламент не
  говорит (там есть только `chmod 777 "$OUT"`); это нужно уточнить у организаторов.
- **Код задач исполняется изолированно.** Тесты задач и программы, написанные моделью, запускаются только
  на копии workspace в `/tmp` и только через обёртку `guard.py`:
  - Landlock (Linux ≥ 5.13; не требует привилегий, работает с `--cap-drop ALL`, `no-new-privileges` и
    файловой системой только для чтения): ядро разрешает дочернему процессу читать лишь установку Python
    и системные библиотеки, а читать и писать — лишь свою копию. Смонтированный каталог задач (включая
    соседние задачи, `task.json` и тесты), копии других задач, `/proc` (окружение харнесса с ключом) и
    `/app` недоступны, в том числе для его потомков. При Landlock ABI ≥ 4 (ядро ≥ 6.7) запрещены и
    TCP-соединения;
  - audit hook Python: отказ в открытии файлов вне копии и в сетевых соединениях через модуль `socket`;
    без Landlock ещё и отказ в запуске процессов и загрузке `ctypes`;
  - лимиты: адресное пространство 4 ГБ, размер файла 128 МБ, вывод не больше 256 КБ на поток (остальное
    читается и отбрасывается), тайм-аут с завершением всей группы процессов;
  - окружение без `LLM_API_KEY`, `LLM_BASE_URL` и переменных харнесса; свой временный каталог.

  Режим изоляции определяется при старте и пишется в лог и в траекторию (`isolation`). Ограничения:
  - на ядре без Landlock остаётся только audit hook — он останавливает обычные программы, но не является
    границей безопасности против намеренно враждебного кода;
  - **сеть при Landlock ABI < 4 ядром не ограничена.** Измерено `tests/net_isolation_probe.py` (свой
    listener на 127.0.0.1, контроль без guard) на ядре 5.15, ABI 1: соединение через модуль `socket`
    отклонено, а через `ctypes`, вложенный `python` из `subprocess` и `bash /dev/tcp` — проходит.
    Файловая изоляция при этом работает: ключа у дочернего кода нет (окружение очищено, `/proc` и `/app`
    недоступны), а доступные адреса определяются сетью контейнера. Закрыть сеть на уровне ядра для
    старых ядер можно фильтром seccomp; он не внедрён, чтобы не менять путь исполнения тестов без
    полной проверки в целевом окружении.

  Запрет в тексте промпта защитой не считается.
- **Харнесс не падает.** Ошибка в одной задаче остаётся в этой задаче; `run_agent.py` всегда завершается
  с кодом 0; сторожевой таймер завершает процесс до часового лимита.
- **`task_type` не обязателен.** Если поля нет или значение неизвестно, тип определяется по содержимому
  workspace и тексту инструкции.
- **Логи openJiuwen** (включая тексты запросов) пишутся в `/tmp`; в консоль выводятся только сообщения
  харнесса.

Переменные окружения (все необязательны, кроме двух первых для LLM-уровня):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY` | — | прокси организаторов |
| `BUDGET` | — | общий бюджет прогона во взвешенных токенах; важнее `TOKEN_BUDGET` |
| `TOKEN_BUDGET` | 1000 × число задач (локальное допущение) | прежнее имя; используется, только если `BUDGET` не задан |

## Ограничения

- Ремонт мутациями принимает правку, если проходят тесты из workspace. Если бы итоговая проверка
  использовала другие, более строгие тесты, часть таких правок могла бы оказаться подгонкой. На синтетике
  40 из 41 исправления совпали по смыслу с эталоном, одно — подгонка под единственный тест.
- Бесплатные решатели рассчитаны на формат примеров. Иные формулировки не угадываются, а передаются
  модели — это стоит токенов и зависит от качества модели.
- Запросы к LLM (тексты промптов, разбор ответов) отлажены на mock-прокси. Сколько токенов тратят и
  насколько точно отвечают настоящие модели `qwen3.8-27b*` на этих промптах, здесь не измерено:
  реальный прогон через прокси организаторов не выполнялся.
- Ответ запасного агента (не coding) принимается без независимой проверки смысла: одна строка вывода
  программы или `ANSWER:`. Для coding проверка есть всегда — тесты задачи.
- Изоляция дочернего кода опирается на Landlock; на ядре без него она слабее (см. «Неочевидные детали»).
- Права на запись в `$TASKS` зависят от того, как организаторы подготовят каталог (см. там же).
- Проверки шли на виртуальной машине с 6 vCPU и 8 ГБ; запуск с `--cpus 8 --memory 16g` из регламента
  на ней воспроизвести нельзя. Полный часовой прогон на 100 задачах не выполнялся.
